# Frontend Review Checklist

React/TS: hook dependency array correctness, predictable state ownership, rerender churn from state/effect misuse, component separation and prop contracts, async cleanup and stale state prevention.

## Performance

- frontend rerender churn from state/hook misuse

## Frontend Deep-Dive

These verify by reasoning about mount/unmount timing and driving the real flow in the running app, not just `npm test` — a green suite passes them by default.

1. **Does the effect actually fire?** For any effect whose body is gated on a condition (`if (status === 'anonymous')`, `if (!user)`), confirm the host component is still mounted when that condition becomes true. If the host only renders in the *other* state (e.g. a chat component that renders only when authenticated) it unmounts on the very transition that would trigger the effect, so the effect is dead. Put lifecycle logic that must observe a teardown transition in an **always-mounted host** (a context provider, the app root), not a leaf that unmounts.
2. **Cross-cutting lifecycle logic belongs at one canonical boundary.** Before adding reset/cleanup/subscribe/unsubscribe logic tied to a session, auth, or route transition, grep for where that transition is *already* handled (`reset()`, `onAuthCleared`, `logout`, existing teardown effects). Place the new logic there and reuse it — don't add a parallel mechanism. Clear state at the boundary where it ends (logout/teardown), not lazily re-applied at the next entry point (login) — otherwise the previous session's data lingers in memory and only the "clear on teardown" path guarantees a clean slate on every exit cause.
3. **No duplication across sibling entry points.** If the same action is needed after `login` and `loginWithGoogle`, or across any parallel handlers, hoist it to the single point they both pass through (a `status`-keyed effect, a shared helper) instead of copy-pasting into each — duplicated lifecycle calls drift out of sync.
4. **Store-field lifecycle.** When adding a field to a shared store, decide explicitly whether `reset()`/teardown must clear it (per-session vs app-lifetime) and confirm both a page reload *and* an in-tab logout→login reach a clean state.
5. **Orphan cleanup after moving/removing logic.** After relocating or deleting a hook, effect, or handler, remove the now-unused imports, `useRef`s, store selectors, and props it left behind — don't leave dead state that reads as intentional (typecheck/lint catch unused bindings; they do not catch an effect that silently never runs).
6. **Validation parity with the canonical implementation.** If this change introduces a new input/action that duplicates an existing capability (a second message-compose box, a second upload/submit flow), grep the canonical implementation (e.g. `MessageComposer.tsx`) for every guard it enforces — length limits, permission checks, rate limits, offline/error handling — and either reuse that component/hook directly or explicitly port each guard. Don't rebuild only the happy path and assume a shared hook (e.g. `useSendMessage`) will reject bad input for you — check whether it actually throws or silently swallows/queues the failure.
7. **i18n key parity.** If the diff adds, removes, or renames a key under `i18n/translations/`, mirror it into every locale listed in `frontend/src/i18n/index.ts`'s `i18nResources` map — never assume `en`/`ja` are the only locales that need updating. Only fix keys this diff touches; leave unrelated pre-existing parity gaps alone.
8. **Mockup fidelity from source, not screenshots.** Before writing classes to match a `mockups/*.html` reference, grep that file's actual CSS for the component (padding, radius, backdrop blur, close-button shape) and copy the concrete values instead of approximating from how a screenshot looks. If an existing component already implements the same mockup pattern correctly (a modal's portal/overlay/padding/close-button conventions), copy its exact structure rather than freehand-building a similar one — a hand-rolled non-portaled overlay will not reproduce a full-page backdrop blur even with the right CSS property.
9. **Live/real-time state completeness.** For any UI element claiming to be live (a presence dot, "Active now", an unread badge), list every server-side lifecycle event that should drive it (explicit change, socket connect/disconnect, logout) and grep the emitting code to confirm each one actually publishes the event your UI listens for — don't assume from the event's name. A gap entirely in untouched code is a pre-existing issue to report, not fix.

   The reverse claim needs its own proof: before reporting that a UI *won't* reflect new server state until a reload, check the consuming query's mount point and `staleTime`, not just the socket/store write paths. A page-scoped React Query hook with no `staleTime` refetches on every mount, so an action performed on a *different* page (`OfficeView`'s audio call-out send) is already reflected by the time the user navigates to the page that reads it — `useChatBootstrap` is consumed only by `ChatPanel` and sets no `staleTime`, which is exactly why PR-198's bootstrap-only preview fix works live in both directions. Enumerating which handlers *don't* write to the Zustand store proves nothing on its own; find the read path and check whether it refetches, and prefer driving the real flow (navigate away, act, navigate back) over reasoning from the write paths alone.
10. **Sibling-pane visibility at shared breakpoints.** When two panes/elements are each hidden by their own independent condition tied to the same responsive breakpoint (e.g. a list pane hidden via `hiddenOnMobile={isCompact && hasSelection}` next to a placeholder pane shown via `isCompact ? 'flex' : ...`), don't verify each condition in isolation — enumerate every combination of (breakpoint × state) and check that at most one pane is visible in each. `frontend/src/components/ChatPanel.tsx`'s list/placeholder pair is the reference example (previously buggy: compact + no selection showed both panes at once, squeezing a two-column layout into a mobile viewport). A passing test suite won't catch this if no test exercises that specific combination — check by reasoning through the truth table, and if screenshotting is feasible, capture the mobile viewport with no selection specifically, not just the states each test already covers.
11. **Client query-cache tenant isolation across account switches.** For any React Query cache keyed by session/account (`['…', orgId, userId]`), the entry lingers for `gcTime` (default 5 min) after the account changes — independently of the Zustand store (item 4). With `staleTime: 0`, switching *back* to the earlier account serves that cached entry immediately (`isLoading: false`, no spinner) before the background refetch, so a `queryFn` that early-returns a *partial* value on a session guard (e.g. `{ summaries: [] }`) poisons its own key and surfaces another account's — or a stale-empty — state on return. Verify the switch-*back* path explicitly (A→B→A shows A's data with a loading state, not B's and not empty), not just that a late response doesn't overwrite the currently-active account. Prefer clearing/invalidating at the session boundary (item 2) over patching inside the `queryFn`. `useChat.ts`'s `useChatBootstrap` is the reference (previously buggy: the mid-switch guard cached `{ summaries: [] }` under the prior account's key).
